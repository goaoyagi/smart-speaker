# feat: composer.py のプロンプト強化（回答の文量・構成・指示語解釈・無関係な検索結果の扱い）

> このファイルは GitHub issue の草案です。内容を確定させたうえで issue として起票してください。
> 出典: `docs/現状分析と改善案_実装順序比較.html`「4案を統合した場合の実装順序」順序2

## 背景

「回答が短すぎる」への**本命の対策**。4案とも「小型モデルは文量の指示がないと最短で打ち切る」と分析している。

現状のプロンプト（`src/composer.py:29-37`）は「日本語のみ」「アルファベット禁止」しか要求しておらず、**回答の分量・構成の指示が一切ない**。しかも末尾が `回答：` の穴埋め形式なので、3B クラスのモデルは最小限で埋めて終了しがち。

```python
prompt = f"""以下の検索結果を『絶対に事実』として扱い、ユーザーの質問に日本語のみで答えなさい。
回答にはアルファベット（英語の単語や文）を含めず、必要であればカタカナや日本語表現に翻訳して出力してください。

{history_block}検索結果：
{context}

質問：{query}

回答："""
```

もう1点、`src/composer.py:29` の「**絶対に事実として扱い**」という強い縛りが、フォローアップ質問時に問題を起こす。指示語だけの発話（「それはどういうこと？」）がそのまま検索クエリになって無関係な結果が返っても、その無関係な結果が「絶対的事実」として注入され、モデルが会話履歴より検索結果を優先してしまう。検索クエリ側の根本対策は順序5（クエリ書き換え）だが、**プロンプト側でも緩和できる**というのが Kimi の提案。

## スコープ

- `src/composer.py` のプロンプト文言の変更のみ。モジュール構成やパイプラインの順序は変えない。
- 順序1（`options` / `system` 追加）とは独立した PR にする。効果を切り分けるため。

## 変更内容

### 1. 検索結果ありの分岐（`composer.py:29-37`）に指示を追加

- **文量・構成の指示**: 「◯〜◯文で、結論を先に述べてから補足を加える形で、具体的に説明しなさい」
- **指示語の解釈指示**: 「『それ』『さっきの』などの指示語は、これまでの会話を参照して解釈しなさい」
- **無関係な検索結果の扱い**: 下記「決めるべき点2」で決定した方針を明記

### 2. 検索結果なしの分岐（`composer.py:39`）にも文量指示を反映

現状は1行のフォールバックだが、検索失敗は非致命でこの経路を通るため、同じ文量指示を効かせる。

```python
prompt = f"{history_block}質問：{query}\n回答（日本語のみ、アルファベット禁止）："
```

### 3. `tests/test_composer.py` を更新

- 追加した指示文がプロンプトに含まれること
- 履歴あり／なし、検索結果あり／なしの4通りで既存の構造が保たれること
- 日本語限定・アルファベット禁止の文言が維持されていること（AGENTS.md の制約が退行していないことの回帰テスト）

## 現状ですでに満たされている点（変更不要）

- **質問はすでにプロンプト末尾**（`回答：` の直前）にある。Fusion の「質問を最後に置いて recency bias を活用する」は現状で対応済みなので、変更は不要。
- 日本語限定・アルファベット禁止の指示は AGENTS.md の必須制約。**削除・弱体化しないこと。**

## 決めるべき点

### 1. 回答の文数

| Fable | Fusion | Kimi | Ultra |
| --- | --- | --- | --- |
| 3〜6文 | 3〜5文 | 3〜5文 | 2〜4文 |

**推奨: 3〜5文**（2案が一致、中央値）。

判断材料: スマートスピーカーなので長すぎても困る。日本語3〜5文は概ね150〜250字で、Piper の読み上げは20〜40秒程度になる見込み。「応答時間が延びてもよい」という前提には収まるが、実機で聞いてみて長すぎるようなら 2〜4文に下げる余地を残す（`.env` で調整できるよう文数を設定値にするかどうかも判断ポイント）。

### 2. 検索結果が質問と無関係だったときの方針 ← **4案で方針が対立**

| 案 | 方針 | プロンプト文言（例） |
| --- | --- | --- |
| Kimi | **無視して答える** | 「検索結果が質問と無関係な場合は、検索結果を無視して、これまでの会話とあなたの知識で答えなさい」 |
| Fusion | **答えない** | 「検索結果に無いことは推測せず『分かりません』と答えなさい」 |
| Fable / Ultra | 言及なし（現状の「絶対に事実」を維持） | — |

**この2つは逆方向の指示**なので、両方を同時に入れることはできない。

- Kimi 案は「フォローアップ質問で文脈が壊れる」問題に効くが、ハルシネーションのリスクは上がる。
- Fusion 案はハルシネーションを抑えるが、無関係な検索結果が混ざるたびに「分かりません」を連発する恐れがある（順序5のクエリ書き換えを入れるまでは、フォローアップのたびに発生しうる）。

**推奨: 折衷案**として、次の2文をセットで入れる。

```
検索結果が質問と無関係な場合は、検索結果を使わず、これまでの会話とあなたの知識で答えなさい。
検索結果を使って答える場合は、検索結果に書かれていないことを推測で補ってはいけません。
```

「検索結果を使うかどうか」をモデルに判断させたうえで、使う場合だけ厳密さを要求する形。

### 3. 出典番号（`[1]` 形式）を付けるか

Fusion のみが提案（検索結果を `[1] タイトル / 本文` 形式で番号付与し、ログに URL を残す）。

**推奨: 今回は見送る。**

理由: プロンプトに番号を入れるとモデルが「1によると」のように出力に混ぜる可能性があり、それを Piper がそのまま読み上げてしまう。AGENTS.md の TTS 安定性の方針と相性が悪い。出典を残す目的は `retriever.py` 側のログ出力で達成できる（順序6の本文取得と一緒に対応するのが自然）。
