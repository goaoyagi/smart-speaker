AIスマートスピーカー 現状分析と改善案

対象リポジトリ: smart-speaker（Raspberry Pi 5 / ローカルRAG構成）｜作成: 2026年7月

要約（TL;DR）
現状の最大のボトルネックは LLM そのものではなく、 (1) Ollama をデフォルト設定（コンテキスト4096トークン・生成オプション未指定）のまま呼んでいること、 (2) LLM に渡す「材料」が検索スニペット（1〜2文）だけで薄いこと、 (3) フォローアップ質問がそのまま検索クエリになり、無関係な検索結果が「絶対的事実」としてプロンプトに注入されること の3点。応答時間に余裕があるなら、「検索前のクエリ書き換え（LLM 1回目）＋上位ページの本文取得と既存Rerankerによるチャンク選別＋回答生成（LLM 2回目）」の構成が最も効果が大きい。

1. 現状のパイプライン

  1. [耳] listener.py: Whisper でユーザーの音声をテキスト化
  2. [検索] retriever.py: 認識テキストをそのまま SearXNG に投げてWeb検索（最大10件）
  3. [並べ替え] retriever.py: 日本語クロスエンコーダ（Optimum/ONNX）で再ランクし上位3件に絞る
  4. [構成] composer.py: 検索結果のタイトル＋スニペットと会話履歴（直近3ターン・回答200文字クリップ）をプロンプトに編成
  5. [脳] brain.py: Ollama /api/generate（qwen2.5:3b、options未指定）で回答生成
  6. [口] speaker.py: piper-tts-plus で発話

2. 精度が出ない具体的な原因

原因1: Ollama の呼び出しがデフォルト設定のまま（回答が短い・文脈が消える の両方に直結）

brain.py は /api/generate に options を一切渡していない。

json_body={
    'model': self.ollama_model,
    'prompt': prompt,
    'stream': False
}
  • コンテキスト長: Ollama の現行仕様では、GPU の無い環境（Pi 5 は CPU 推論）の既定 num_ctx は 4096トークン。一方 brain.py は prompt[:10000] と1万文字まで許容しており、日本語はほぼ1文字≒1トークン以上なので、履歴＋検索結果を含むプロンプトは容易に 4096 を超える。Ollama はバッファが溢れると古いトークン（＝プロンプト冒頭）から捨てるため、「日本語のみ」の指示・会話履歴・検索結果の前半が黙って消える。「会話コンテキスト保持が効かない」症状の有力な直接原因。
  • 生成長・温度: num_predict（最大生成トークン数）や temperature、repeat_penalty が未指定で、小型モデルは指示がなければ短く切り上げがち。「回答が短すぎる」の一因。
原因2: LLM に渡す事実ソースが「検索スニペット」だけで薄い

composer.py がコンテキストとして使うのは SearXNG が返す title と content（スニペット）のみ。スニペットは各1〜2文しかないため、Reranker で上位3件に絞っても LLM の手元にある情報量は合計数百文字程度。材料が薄ければ、どんなにプロンプトを工夫しても回答は短く浅くなる。Reranker 導入で「どれを渡すか」は改善したが、「渡すものの中身」が改善されていない。

原因3: フォローアップ質問が生のまま検索クエリになる

main.py の処理順を見ると、会話履歴はプロンプト構成にしか使われず、検索には使われていない。「それはどういうこと？」のような発話がそのまま SearXNG に投げられ、無関係な検索結果が返る。しかもプロンプトはその結果を「絶対に事実」として扱えと指示しているため、無関係な情報が会話履歴より優先され、文脈が壊れる。「会話コンテキストが効かない」のもう一つの主因。

原因4: 履歴の持ち方が単発テキスト生成向け
  • conversation_history.py は直近3ターン・回答200文字クリップの平文要約で、/api/generate の単発プロンプトに文字列として埋め込んでいる。Qwen2.5 はチャット調整済みモデルなので、/api/chat で system / user / assistant のロール付きメッセージとして履歴を渡す方が、指示追従・文脈参照ともに素直に効く。
  • プロンプト側にも system 指示が分離されておらず、「日本語のみ」ルール・事実指示・履歴・質問が1本の文字列に混在している。

3. 改善案（優先度順）

前提: AGENTS.md の制約（生成前RAGの順序維持・生成後検証への設計変更禁止・日本語限定指示の維持）はすべて守れる範囲での提案。

案1【最優先・依存追加なし】Ollama 呼び出しの適正化
  • brain.py で options を明示指定する: num_ctx（Pi 5 の 8GB なら 8192 が現実的。ollama ps の CONTEXT 列で実際の割当を確認）、num_predict（例: 512）、temperature（0.2〜0.3、事実ベース回答向け）、repeat_penalty。値は config.py ＋ .env.example に追加。
  • /api/generate → /api/chat へ移行し、system メッセージに「日本語のみ・アルファベット禁止・検索結果を事実として扱う・3〜6文程度で具体的に答える」を固定で置く。回答の長さの明示指示は「短すぎる」対策として即効性がある（スマートスピーカーなので長すぎも禁物。目標長の指定が正解）。
  • 会話履歴は平文要約ではなく user / assistant のロール付きメッセージとして渡す（ConversationHistory に messages 形式の出力を追加）。

変更範囲は brain.py・composer.py・conversation_history.py・config.py で、外部依存の追加はゼロ。費用対効果が最も高い。

案2【LLM 2回呼び・依存追加なし】検索前のクエリ書き換え（Condense Question）

履歴が存在する場合、検索の前に LLM を1回呼び、「会話履歴＋今回の発話」から自己完結した日本語検索クエリを生成させる（例:「それはどういうこと？」→「◯◯とは何か 意味」）。書き換えたクエリで SearXNG → Reranker を実行する。

  • 生成前RAGの順序（検索→構成→生成）は崩れない。検索の前段が1ステップ増えるだけ。
  • 3Bモデルでもクエリ書き換え程度なら十分こなせ、追加レイテンシは数秒程度。書き換え失敗時は元の発話で検索するフォールバックにすれば非致命の方針にも合う。
  • フォローアップ質問時の「無関係な検索結果が事実として注入される」問題を根本的に解消する。
案3【新ライブラリ導入】上位ページの本文取得＋チャンク単位の再ランク

Reranker で選んだ上位1〜3件の URL について本文を取得し、スニペットの代わりに本文チャンクをコンテキストにする。

  • 本文抽出には trafilatura（純Python寄りで Pi でも軽量、日本語ページの本文抽出精度が高い）を推奨。代替は readability-lxml。
  • 本文を500〜800文字程度のチャンクに分割し、既存の ONNX クロスエンコーダをそのまま流用して「質問 vs チャンク」で再ランクし、上位数チャンクだけをプロンプトへ。導入済みの Reranker 資産が2度活きる。
  • 取得失敗はスニペットへのフォールバックとし、SearchError 系の非致命方針を維持。
  • HTTP 取得は http_client.py 経由に拡張（現在 JSON 専用のため HTML 取得関数の追加が必要）。

「回答が短い・浅い」への最も本質的な対策。追加レイテンシはページ取得＋再ランクで数秒〜10秒程度。

案4【LLM 複数回呼び・発展形】チャンクごとの事実抽出（Map-Reduce）

案3をさらに進め、取得した各ページ（またはチャンク群）に対し「この質問に関係する事実だけを日本語で箇条書きに抽出せよ」という LLM 呼び出しを行い（Map）、抽出済みの事実リストを最終プロンプトに渡して回答生成（Reduce）する。

  • 小型モデルは「長い雑多なコンテキストから取捨選択して回答する」のが苦手で、「短い作業を確実にこなす」のは得意。3Bモデルとの相性が良い構成。
  • すべて生成「前」の処理のため、生成後検証禁止の制約にも抵触しない。
  • レイテンシはページ数×1回の推論（Pi 5 の 3B で各10〜20秒程度）増えるため、案1〜3の効果を見てから判断するのがよい。
案5【設定変更のみ】モデルの見直し

一言でいうと、「頭脳として使うAIモデル自体を、より新しく賢いものに交換する」提案。現在は .env の OLLAMA_MODEL=qwen2.5:3b で「Qwen2.5 の 3B（30億パラメータ）」を使用している。パラメータ数はざっくり「脳の大きさ」で、大きいほど賢いが、必要なメモリと時間も増える。

なぜ交換で精度が上がるのか

  1. 世代が新しいモデルは同じサイズでも賢い。 Qwen2.5 は2024年のモデルで、その後により新しい世代（例: Qwen3 系）が出ている。同じ 3〜4B クラスでも、新世代のほうが日本語力・指示の守り方・回答の充実度が向上している（車と同じで「排気量が同じでも新型のほうが性能がいい」イメージ）。
  2. 少し大きいサイズも選択肢に入る。 応答が遅くなってもよい前提なら、3B より大きいモデルも候補になる。

なぜ「7Bではなく4Bクラス」を勧めるのか

ラズパイ5のメモリ（8GB想定）は、「モデル本体」と「会話の作業スペース（コンテキスト）」の2つで取り合いになる。

  • 7Bモデルを入れると、モデル本体だけでメモリの大半（約4.5GB＋OS等）を食ってしまい、案1で広げたい作業スペース（num_ctx）を確保する余裕がなくなる。せっかく検索結果の本文や会話履歴をたくさん渡せるようにしても、置き場所がない状態になる。
  • 4Bクラスの新世代モデルなら、本体は約2.5〜3GBで済むので、作業スペースを広め（8192トークン）に取れる。「そこそこ賢い頭脳＋広い机」の組み合わせのほうが、「賢い頭脳＋狭すぎる机」より総合的に良い結果になる。

やることは設定変更だけ

ollama pull qwen3:4b        # 新しいモデルをダウンロード

.env の OLLAMA_MODEL=qwen2.5:3b を OLLAMA_MODEL=qwen3:4b に変えれば切り替わる。元に戻すのも1行なので、試して悪ければすぐ戻せる、リスクの低い改善策。

注意点

  • 3B→4Bになるぶん、回答生成は1.2〜1.5倍ほど遅くなる見込み。
  • 「どちらのモデルが本当に良いか」は体感だと判断がぶれるので、案1〜3を先に入れて土台を整えてから、同じ質問を両方のモデルに投げて聞き比べる（A/B比較）のがおすすめ。

4. 併せて直したい小さな点

  • CONVERSATION_ANSWER_CLIP=200 は案1で num_ctx を拡大すれば 400〜600 に引き上げられ、フォローアップの成立率が上がる。
  • brain.py の prompt[:10000] は「文字数での切り詰め」であり先頭が残り末尾（＝質問）が消える方向のため、案1実施時に見直しが必要。
  • 「音声が検出されませんでした」系の定型発話が last_answer を上書きしない現仕様は維持すべき（変更不要の確認事項）。

5. 推奨する進め方
