AGENTS.md 書き換え案

対象リポジトリ: smart-speaker｜「現状分析と改善案」の改善案（案1〜5）を実装する前提での AGENTS.md 見直し｜作成: 2026年7月

要約
改善案（特に案1〜4）を実装する場合、AGENTS.md のいくつかのルールが文言どおりに読むと改善案と矛盾し、AIエージェントが「ルール違反だ」と判断して作業を拒否したり、中途半端な実装をしたりする原因になる。 項目1と2は実装前に必ず修正すべき（放置すると改善案の実装自体がルール違反になる）。項目3と4は該当する案を実装するタイミングで修正すればよく、項目5は任意。

1. 「生成前RAGの処理順序」の定義 最重要

矛盾する改善案: 案2（検索前のクエリ書き換え）／案4（検索後の事実抽出）

現在の文言 生成前RAG の処理順序を崩さない（検索 → プロンプト構成 → 生成）。生成後検証への設計変更はしない。

案2（検索前にLLMでクエリ書き換え）や案4（検索後にLLMで事実抽出）は、「検索 → 構成 → 生成」の間にLLM呼び出しを挟むため、厳密に読むと順序違反に見える。このルールの本来の意図は「最終回答の生成は必ず検索の後」「生成後に検証・修正しない」のはずなので、意図が伝わる形に書き換える。

書き換え案 生成前RAG の原則を崩さない: 最終回答の生成は、必ず検索とコンテキスト構成の後に1回だけ行う。生成後の検証・修正フローへの設計変更はしない。クエリ書き換えや事実抽出など、最終回答生成より前の補助的なLLM呼び出しは追加してよい。

2. エラー方針の粒度 最重要

矛盾する改善案: 案2（クエリ書き換え）／案3（ページ本文取得）

現在の文言 生成（GenerationError）の失敗は致命。

案2のクエリ書き換えもLLM呼び出しなので、素直に実装すると失敗時に GenerationError が飛び、現行ルールでは致命扱いになる。しかし書き換え失敗は「元の発話でそのまま検索する」でよく、致命にすべきではない。案3のページ本文取得の失敗も「スニペットにフォールバック」で継続すべき。次のような追記が必要。

書き換え案（追記）
  • 最終回答の生成（GenerationError）の失敗は致命。ただし、クエリ書き換え・事実抽出など補助的なLLM呼び出しの失敗は非致命とし、フォールバック（元のクエリで検索、抽出をスキップ等）で処理を続行する。
  • 検索結果ページの本文取得の失敗は非致命。スニペットにフォールバックする。

3. 日本語限定指示の「置き場所」の固定 案1実装時に修正

矛盾する改善案: 案1（/api/chat 移行・system メッセージ導入）

現在の文言 composer.py のプロンプトが持つ日本語限定・アルファベット禁止の指示を維持する。

案1で /api/chat に移行すると、この指示は composer.py 内の文字列から system メッセージへ移動する可能性が高く、ファイル名まで固定した現文言だと矛盾する。守りたいのは指示の存在であって場所ではない。

書き換え案 日本語限定・アルファベット禁止の指示を、プロンプトまたは system メッセージのどこかで必ず維持する。

4. HTTPクライアントの関数名の固定 案3実装時に修正

矛盾する改善案: 案3（ページ本文＝HTMLの取得）

現在の文言 HTTP 通信は src/http_client.py の http_get_json / http_post_json を使う。

案3ではHTML本文の取得が必要で、JSON専用の既存2関数では対応できない。「http_client.py に集約する」という意図を残しつつ関数を固定しない文言にする。

書き換え案 HTTP 通信は src/http_client.py に集約する（既存は http_get_json / http_post_json。必要なら同ファイルに関数を追加する）。requests を各モジュールで直接呼ばない。

5. future_extensions.md の記述が古い 任意

AGENTS.md は「future_extensions.md の機能は明示的な依頼がない限り着手しない」としているが、future_extensions.md に載っている5項目のうち 2（ステータスLED）・4（会話履歴）・5（プッシュ・トゥ・トーク）はすでに実装済み。エージェントが「会話履歴の改善は future_extensions.md の項目だから着手禁止では？」と誤読するリスクがある。実装済み項目を future_extensions.md から削除（または「実装済み」と明記）するのが望ましい。これは AGENTS.md 本体ではなく参照先の修正。

変更不要なもの

  • テスト方針（外部サービス・ハードウェアのモック必須、srcミラー構成）はどの案とも矛盾しない。案2〜4で追加するLLM呼び出しも既存の Ollama モック方針がそのまま使える。
  • コミット/PRルール、speaker.py・status_led.py の個別ルールも影響なし。
  • 案5（モデル差し替え）は .env の変更だけなので AGENTS.md の修正は不要。
