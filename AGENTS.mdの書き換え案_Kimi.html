改善案を実装する前提で AGENTS.md を精査すると、現状の書き方だと改善策と衝突する制約が3つあります。以下、現行の記述・問題点・改訂案の順に示します。

1. 書き換えた方がいい制約

1-1. 生成前RAGの処理順序 —— 多段化の余地を明示すべき

現行の記述

生成前RAG の処理順序を崩さない（検索 → プロンプト構成 → 生成）。生成後検証への設計変更はしない。

問題点が2つあります。

  • Reranking が抜けている。実態は「検索 → Reranking → プロンプト構成 → 生成」で、project_context.md 側には記載があるのに AGENTS.md 側と不一致
  • クエリ書き換え（改善案B1）や検索要否判定（B2）のような生成の前段に LLM 呼び出しを挟む改善が、文面上は順序違反に読めてしまう。将来のエージェント（や人間）が「順序を崩すな」と解釈して着手を躊躇するリスクがある
改訂案 
- **生成前RAG** の基本順序を崩さない（検索 → Reranking → プロンプト構成 → 生成）。
  - 生成前の多段化は許可する：クエリ書き換え（検索の前）、検索要否判定（検索の前）、
    本文フェッチ（検索の後）、エビデンス抽出（Reranking の後）など。
  - 生成後に LLM を再呼び出しして検証・推敲する設計（生成後検証）は導入しない。

なお「生成後検証を禁止する」思想自体は、小型LLMでは検証器も弱く効果が薄い・遅延が倍増するという点で妥当だと考えます。もし将来「下書き→推敲」まで許容したくなったら、この一文の緩和を別途判断する形がよいです。

1-2. 日本語のみ制約 —— 「最終回答」への適用限定と、指示の置き場所の非固定化

現行の記述

回答は日本語のみ（アルファベットを含めない）。TTS の安定性のため、composer.py のプロンプトが持つ日本語限定・アルファベット禁止の指示を維持する。

問題点が2つあります。

  • 「composer.py のプロンプトが持つ」と場所が固定されている。改善案の system プロンプト導入（A1）や /api/chat 移行（D1）をすると、指示の置き場所が composer のプロンプト文から system メッセージに移るので、文字通り守ると矛盾する
  • 中間的な LLM 呼び出しまで日本語限定にする必要はない。クエリ書き換えの出力（検索クエリ）は発話されないので、アルファベットの固有名詞を許した方がむしろ SearXNG の検索精度が上がる
改訂案 
- **最終的に発話する回答**は日本語のみ（アルファベットを含めない）。TTS（piper-tts-plus）の安定性のため。
  この指示はプロンプトまたはシステムメッセージのいずれかの形で必ず維持する（置き場所は composer.py に限定しない）。
- クエリ書き換え・検索要否判定など、発話されない中間的な LLM 呼び出しの出力にはこの制約を適用しない
  （検索クエリにアルファベットの固有名詞を含めることを許可する）。

1-3. エラー方針 —— 補助的な LLM 呼び出しを非致命として明記

現行の記述

main.py のエラー方針に合わせる:

・検索失敗（SearchError）は非致命。空コンテキストで処理を続行する。

・録音・認識（ListenerError）・生成（GenerationError）・発話（SpeakerError）の失敗は致命。

問題点： クエリ書き換えや Router の失敗は GenerationError として表面化するので、現行ルールだと致命扱い＝会話ターン全体が落ちる。補助処理が落ちても元の質問で続行できるのが本来あるべき姿で、Reranker 失敗時のフェイルソフト設計とも思想的に同じですが、明文化されていません。

改訂案 
- `main.py` のエラー方針に合わせる:
  - 検索失敗（`SearchError`）は**非致命**。空コンテキストで処理を続行する。
  - 補助的な LLM 呼び出し（クエリ書き換え・検索要否判定・エビデンス抽出）の失敗も**非致命**とし、
    補助処理をスキップして元の入力で処理を続行する（Reranker 失敗時のフォールバックと同じ考え方）。
  - 最終回答の生成（`GenerationError`）・録音・認識（`ListenerError`）・発話（`SpeakerError`）の失敗は**致命**。

2. 任意： 追記を検討したいもの

「新規依存は最小限に」の判断基準の明文化。本文フェッチ用の trafilatura 導入（改善案C1）はこのルールと緊張関係にあるので、基準を書いておくと判断がぶれません。

追記案 
- 新規依存は最小限に。追加する場合は Raspberry Pi（ARM64）での動作実績・メモリ使用量・
  起動時間への影響を確認し、PR に根拠を記載する。

3. 書き換えない方がいいもの

  • 生成前RAGの根本思想と日本語回答の根本方針： ハルシネーション対策とTTS安定性の要なので維持
  • テスト規則・コミット/PR規則： 新しい LLM 呼び出しにもそのまま適用可能（モック化・ミラーテスト追加・.env.example 更新の各ルールでカバーできる）
  • アルファベット禁止そのもの： 「TTS前処理で英語→カタカナ変換（fugashi/UniDic活用）に移してプロンプト側の禁止を緩和する」という抜本改革も理論上は可能ですが、変換精度のリスクが大きく、現時点ではプロンプト側での禁止維持が安全です

4. 反映時の注意

AGENTS.md を改訂する際は project_context.md 側の「生成前RAGの処理順序を崩さないこと」等の記述と文言の整合を取ることも忘れないようにしてください（片方だけ更新すると、次のエージェントが矛盾した指示を読むことになります）。変更はルール自身の定めに従い、feature ブランチ＋プルリクエストで統合します。
