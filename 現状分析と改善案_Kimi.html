1. 現状のパイプライン

コードを読んだ限り、構成自体は教科書通りの生成前RAGで、むしろよく整理されています。

  • retriever.py: SearXNG で候補10件取得 → ONNX クロスエンコーダで Top3 に Rerank
  • composer.py: 検索結果＋履歴文字列を単発プロンプトに埋め込み
  • brain.py: Ollama /api/generate に1回 POST（qwen2.5:3b）
  • conversation_history.py: 直近3ターンを保持し、回答は200字にクリップして文字列化

つまり問題はアーキテクチャではなく、プロンプト設計・材料の薄さ・検索クエリの劣化にあります。

2. 症状ごとの原因分析

2.1 「回答が短すぎる」の原因： 生成設定ではなくプロンプトと材料

まず一点、よくある誤解を潰しておくと、Ollama の num_predict デフォルトは -1（無制限） です（ドキュメントの「128」は誤記と公式 issue で訂正済み）。つまりトークン上限で切られているわけではありません。

実際の原因は以下です。

① プロンプトに文量・構成の指示が一切ない

src/composer.py（29〜37行）

prompt = f"""以下の検索結果を『絶対に事実』として扱い、ユーザーの質問に日本語のみで答えなさい。
回答にはアルファベット（英語の単語や文）を含めず、必要であればカタカナや日本語表現に翻訳して出力してください。

{history_block}検索結果：
{context}

質問：{query}

回答："""

「答えなさい」だけだと、3Bクラスのモデルは最小限の応答で打ち止めする傾向が強いです。「3〜5文で具体的に説明しなさい」のような指示があるだけで出力長は明確に変わります。

② 材料（エビデンス）が薄い

RERANK_TOP_K=3 × SearXNG のスニペットは各1〜2行（100〜300字程度）。材料が少なければ、どんなに指示しても回答は膨らみません。「絶対に事実として扱え」という強い縛りも、スニペットの表層的な言い換えで終わらせる方向に働いています。

③ system プロンプト未指定

src/brain.py（35〜39行）

json_body={
    'model': self.ollama_model,
    'prompt': prompt,
    'stream': False
},

/api/generate は raw 未指定だとモデルのチャットテンプレートが適用され、system を渡さないと Qwen 既定の英語の汎用システム文言が暗黙に挿入されます。日本語専用アシスタントとしての振る舞いが不安定になる一因です。

2.2 「会話コンテキストが効かない」の原因： 追質問をそのままWeb検索に投げている

これが最大の構造的問題です。

src/main.py（140〜151行）

# --- Web search (non-fatal: degrade to no-context prompt) ---
self.status_led.set_state(LedState.SEARCHING)
try:
    search_results = self.retriever.search_web(text)
except SearchError as e:
    logger.warning("Search failed, proceeding without context: %s", e)
    search_results = []

# --- Compose & generate (include condensed conversation history) ---
self.status_led.set_state(LedState.THINKING)
history_context = self.history.as_condensed_context()
prompt = self.composer.compose_prompt(text, search_results, history_context)

「それはどういうこと？」「もっと詳しく」のような照応・省略を含む追質問が、そのまま search_web(text) に渡されます。すると：

  1. SearXNG は無関係な結果を返す（「それは」では検索できない）
  2. Reranker は「質問との関連度で並べ替える」だけなので、そもそも無関係な候補群からは救えない
  3. その無関係な結果を composer が「絶対に事実として扱いなさい」とモデルに渡す
  4. モデルは履歴より検索結果を優先 → 文脈が破壊される

履歴の保持自体は実装済みですが、現在の質問を自立した質問に書き換える処理（Condense-Question）がないため、履歴が検索・Rerank・生成のどこにも活きていません。future_extensions.md 第4項でも「過去の対話履歴を要約して現在の質問に統合」が構想されていた部分で、現状は「プロンプトへの履歴埋め込み」までしか実装されていない状態です。

2.3 副次的な要因

  • Whisper の誤認識: transcribe() で initial_prompt 未使用。固有名詞を誤認識すると検索クエリごと壊れる
  • 検索不要な発話でも必ず検索: 挨拶や雑談への無関係な検索結果も「絶対的事実」として注入される

3. 改善提案（優先度順）

AGENTS.md の制約（生成前RAGの順序を崩さない／日本語のみ／検索失敗は非致命）に整合する範囲で設計しています。

A追加遅延ゼロで効く施策（変更ごく小）

A1. brain.py に options / system / keep_alive を追加

json_body={
    'model': self.ollama_model,
    'prompt': prompt,
    'stream': False,
    'system': 'あなたは日本語専用の音声アシスタントです。回答はすべて日本語のみで行い、アルファベットを含めてはいけません。',
    'keep_alive': '30m',
    'options': {
        'temperature': 0.3,      # 事実忠実性を優先して下げる
        'num_ctx': 4096,
        'num_predict': 512,      # 上限として（暴走防止。短縮目的ではない）
        'repeat_penalty': 1.1,
    },
}

system でテンプレート既定の英語システム文言を上書きし、日本語応答が安定します。keep_alive は後述の複数回呼び出し導入時のロード待ち解消に必須です。設定値は config.py 経由＋.env.example 更新のルールに従ってください。

A2. composer.py のプロンプト強化

  • 「検索結果の内容をもとに、3〜5文で具体的に説明しなさい」（文量指示）
  • 「『それ』『さっきの』などの指示語は『これまでの会話』を参照して解釈しなさい」
  • 「検索結果が質問と無関係な場合は、検索結果を無視してこれまでの会話と一般知識で答えなさい」

最後の一文が重要で、無関係な検索結果による文脈汚染をプロンプトレベルで緩和できます。

A3. Whisper initial_prompt に直前話題を渡す

listener.py の1行追加レベル。誤認識由来の検索劣化を緩和します。

BLLM複数回呼び出し（生成前RAGの順序は維持）

B1. 検索前クエリ書き換え（最重要の提案）

履歴が存在する場合、検索の前に LLM を1回呼び、「履歴＋最新の質問 → 単独で意味が通じる検索クエリ1文」を生成し、それを SearXNG に投げます。

履歴: 「太陽光発電の仕組みは？」→「…光電変換を利用して…」
今の質問: 「それの欠点は？」
書き換え後: 「太陽光発電の欠点」
  • 「それは」が具体的な名詞句に解決されるので、SearXNG と Reranker の両方が本来の精度で動くようになる
  • 3Bモデルでも「書き換え」だけなら安定してこなす。temperature 0・num_predict 64 で +5〜10秒程度
  • 失敗時は元の質問で検索にフォールバック（「検索失敗は非致命」の既存方針と同じ扱い）
  • 処理順序は「検索 → 構成 → 生成」のまま。クエリ生成は検索ステップの前段処理であり、生成前RAGの設計制約に抵触しません

B2. 検索要否の判定（Router）

LLM1回（はい/いいえの短答）で「この質問にWeb検索が必要か」を判定し、雑談・履歴参照のみの質問では検索自体をスキップ。ノイズ注入を根本から断ちます。スキップした分、実質的な遅延は相殺される場面もあります。

B3. エビデンス抽出（任意・重め）

Rerank 後のスニペットから「質問に関連する事実のみ箇条書きで抽出」を LLM にさせてから composer に渡す案もありますが、3B だと抽出漏れのリスクと +15〜30秒 のコストがあるため、B1導入後に効果を見てから判断でよいと考えます。

なお「下書き→推敲」「生成後の自己検証」型の多段生成は、AGENTS.md の「生成後検証への設計変更はしない」に抵触し得るため今回は提案しません。生成前の多段化（B1/B2/B3）で精度を稼ぐのが、このリポジトリの制約と相性のよい方向です。

Cコンテキストの密度向上（新ライブラリ導入）

C1. 本文フェッチ（trafilatura 導入）——「短い回答」への最も根本的な処方

Rerank 上位1〜2件の URL から記事本文を抽出し、先頭800〜1200字をコンテキストに追加します。現状はスニペット1〜2行しか材料がないので、長く正確な回答を作る土台自体が不足しています。trafilatura は依存が軽くラズパイでも実用的に動作する本文抽出ライブラリです。タイムアウト3秒・失敗は非致命（スニペットのみで継続）という設計にすれば、既存のエラーポリシーとも整合します。

C2. 候補数・採用数の増量

RERANK_TOP_K 3→5、SEARCH_CANDIDATE_LIMIT 10→20 に増量（num_ctx 4096 と併せて）。.env 変更のみで試せます。

D構造改善

D1. /api/chat への移行

履歴を文字列ではなく messages 配列（user/assistant ペア）で渡す方式に変更。Qwen系はチャットフォーマットで訓練されているため、多ターンの文脈解釈が大きく改善します。conversation_history.py に as_messages() を追加し、brain.py の POST 先を /api/chat に変える形です。

D2. モデル変更の検討

精度改善の一番単純な手段はモデル自体の更新でもあります。Pi 5（8GB）の2026年実測ベースでは：

モデル速度（実測）備考
現行: Qwen2.5 3B Q4_K_M約8 tok/s現状
LFM2.5 1.2B JP約15 tok/s日本語チューニング済み。速くて日本語会話向き
Qwen3.5 2B約3.7 tok/s（Q8）新世代だがPiではやや重い
Gemma 3 4B Q4_K_M約3.6 tok/s精度重視なら選択肢。「応答時間は許容」とのことなので検討余地あり

OLLAMA_MODEL を変えるだけで試せるため、A/B/C の改善後にそれでも不足なら検討、という順序が無難です。
